## 1. 의도 분석 (Intent Analysis)

- **사용자 요청**: `REQUIREMENTS.ko.md`의 요구사항을 기반으로 여러 프로젝트의 앱·창·브라우저 탭·폴더를 "작업 묶음"으로 저장·복원하는 크로스플랫폼 데스크톱 앱 개발.
- **요청 유형**: New Project (Greenfield)
- **범위(Scope)**: System-wide / Cross-platform — macOS + Windows 데스크톱 애플리케이션, 다중 컴포넌트(UI, 도메인, 저장, OS 어댑터, 브라우저 어댑터)
- **복잡도(Complexity)**: Complex — OS별 접근성/자동화 API 연동, 브라우저 탭 식별, 상태 동기화, 견고한 저장
- **명확도(Clarity)**: Clear — 상세한 기능/화면/데이터/인수 조건 제공

## 2. 목적 및 대상 사용자

**목적**: 사용자가 여러 프로젝트를 오갈 때 필요한 앱·창·브라우저 탭·폴더를 하나의 작업 묶음으로 저장하고, 선택 한 번으로 이전 작업 환경을 빠르게 복원한다.

**주요 사용자**:
- 여러 프로젝트를 동시에 진행하는 개발자·디자이너
- 브라우저·편집기·터미널·파일 관리자를 함께 쓰는 사용자
- 업무별 창 구성을 반복해서 열고 전환하는 사용자

## 3. 기능 요구사항 (Functional Requirements)

각 요구사항에는 추적을 위한 ID를 부여한다. (FR-그룹번호)

### FR-1 작업 묶음 관리
- **FR-1.1** 작업 묶음을 생성·삭제할 수 있어야 한다. ~~이름 변경~~ → **[1.1 연기]** 이름 변경 UI/커맨드는 현 반복 범위 밖(백로그 `#D-32`). 생성 시 이름 지정으로 대체한다.
- **FR-1.2** 하나의 작업 묶음에 여러 리소스를 저장할 수 있어야 한다. **[1.1 연기]** 묶음에서 **개별 리소스를 제거**하는 경로는 미구현이며 **P1 백로그**로 유지한다(잘못 등록한 항목을 되돌릴 수 없는 실사용 공백 — `#D-33`). 도메인 `WorkBundle::remove_resource`는 이미 존재하므로 커맨드/UI 배선만 남았다.
- **FR-1.3** 작업 묶음 삭제 전 확인 절차를 제공해야 한다.
- **FR-1.4** 작업 묶음과 리소스는 앱 재실행 후에도 유지되어야 한다. (→ AC-1, AC-12)

### FR-2 실행 중인 항목 표시
- **FR-2.1** 실행 중인 일반 앱 창과 브라우저 탭을 왼쪽 패널에 표시한다.
- **FR-2.2** 같은 앱의 창이 여러 개면 앱 아이콘은 한 번만 표시하고 창 제목을 아래에 나열한다.
- **FR-2.3** 각 앱은 OS의 실제 앱 아이콘을 표시한다. (→ NFR, FR-7)
- **FR-2.4** 현재 선택된 창은 여러 창 그룹 안에서만 녹색 점으로 구분한다.
- **FR-2.5** 검색어로 실행 중인 항목을 필터링할 수 있어야 한다.
- **FR-2.6** 항목 더블 클릭 시 해당 창/탭을 최전면으로 가져온다. (→ AC-2)
- **FR-2.7** 닫힌 창, 시스템 보조 창, 중복 브라우저 탭은 목록에서 제외한다. (→ AC-7)
- **FR-2.8** (신설 2026-09-08) 앱 항목을 클릭하면 해당 앱의 **현재 실행 중인 창/탭 목록**을 앱 아래에 펼치고(expand) 다시 클릭하면 접는다(collapse). 펼쳐진 목록의 각 창/탭은 **구분 가능한 제목**을 표시하며, 개별 창/탭을 선택하면 FR-2.6/FR-4.1에 따라 정확히 그 창/탭만 최전면으로 가져온다. 창/탭이 **하나뿐인 앱도 동일한 데이터 모델·상호작용**으로 처리한다(펼침 결과가 1개 항목일 뿐, 앱 클릭 즉시 임의 창을 활성화하지 않는다 — cf. FR-4.2). 실행 종료된 창/탭은 주기 갱신(FR-7.4) 시 목록에서 자동 제거한다. 이 상호작용은 기존 리소스 등록 드래그(FR-3.1) 및 작업 묶음 기능을 방해하지 않는다.

> **정합화 노트 (2026-09-08)**: FR-2.2/FR-2.4/FR-2.6 및 FR-4.1/FR-4.2는 **원래부터 창 단위 열거 + 정확한 창 활성화**를 규정한다. 그러나 `REQUIREMENTS.ko.md §13.1/§13.4`의 사후 명확화(2026-09-08)와 출하 코드는 이를 **앱 단위**(프로세스당 대표 창만 열거·이름 dedup, 앱 클릭 시 아무 창이나 포커스)로 좁혀 시행했다(→ `known-deviations.md#B1`, `#G1`). FR-2.8은 원 설계인 **창 단위 모델**로 재정렬하고, 앱 그룹핑 위에 명시적 **펼침/접기** 어포던스를 추가한다. §13.1/§13.4는 이에 맞게 개정되었다.

### FR-3 리소스 등록
- **FR-3.1** 실행 중인 항목을 작업 묶음으로 드래그하여 추가할 수 있어야 한다. (→ AC-3)
- **FR-3.2** ~~작업 묶음의 추가 버튼으로 실행 중인 창을 선택해 추가~~ → **[1.1 범위 제외]** 등록 경로를 **드래그 앤 드롭(FR-3.1) 단일 경로**로 확정한다. 버튼 기반 선택 등록은 중복 어포던스로 판단하여 제외(`#D-34`).
- **FR-3.3** ~~파일·폴더·앱 실행 파일·웹 주소를 직접 끌어다 놓아 추가~~ → **[1.1 범위 제외 — 기술적 상충]** OS 파일 드롭(Tauri `dragDropEnabled`)과 실행앱 패널의 HTML5 드래그(FR-3.1)는 **동일 창에서 공존할 수 없다**. 커밋 `1ae75df`에서 FR-3.1을 살리기 위해 `dragDropEnabled: false`로 OS 드롭을 껐고, 본 개정으로 그 트레이드오프를 정식 확정한다(`#D-35`).
  > **되돌릴 근거**: 향후 OS 드롭이 필요해지면 (a) 전용 드롭 존만 네이티브 드롭을 받거나 (b) 실행앱 패널 드래그를 포인터 이벤트 기반으로 재구현하는 두 경로가 있다. 어느 쪽도 현 반복에는 넣지 않는다.
- **FR-3.4** 같은 작업 묶음에 동일한 창을 중복 등록하지 않는다. (→ AC-3)
- **FR-3.5** 같은 앱의 서로 다른 창, 경로가 다른 폴더, 같은 주소를 연 서로 다른 탭은 별도 항목으로 등록할 수 있어야 한다. (→ AC-4, AC-5, AC-8)

### FR-4 개별 항목 활성화
- **FR-4.1** 저장된 항목 선택 시 정확히 그 창/탭을 최전면으로 가져온다. (→ AC-2)
- **FR-4.2** 앱만 활성화하고 다른 창을 보여주는 동작은 성공으로 처리하지 않는다.
- **FR-4.3** 등록된 창이 닫혀 있으면 가능한 경우 저장된 문서·폴더·웹 주소를 다시 연다. (→ AC-9)
- **FR-4.4** 다시 열린 창을 발견하면 이후 같은 항목으로 추적한다. (→ AC-9)

### FR-5 작업 묶음 전체 활성화
- **FR-5.1** 한 번의 동작으로 작업 묶음의 모든 항목을 활성화할 수 있어야 한다.
- **FR-5.2** 항목은 저장된 순서대로 처리한다.
- **FR-5.3** 일부 항목이 실패해도 나머지 항목은 계속 처리한다. (→ AC-11, SECURITY-15)
- **FR-5.4** 완료 후 성공·미발견·오류를 사용자에게 알린다.

### FR-6 항목 편집 — **[1.1 전체 연기]**
> FR-6.1~6.3은 **현 반복 범위 밖**으로 연기한다(`#D-31`). 편집 UI·커맨드가 전혀 없으며, 등록 정보는 드래그 시점 값으로 고정된다. **삭제가 아니라 연기**이며 백로그에 유지한다 — 특히 FR-6.2(닫힌 항목의 재실행 주소 수정)는 FR-4.3의 실효성을 좌우하므로 차기 반복 우선 후보다.
- **FR-6.1** *(연기)* 항목의 표시 이름을 변경할 수 있어야 한다.
- **FR-6.2** *(연기)* 닫힌 항목 재실행에 사용할 웹 주소나 경로를 수정할 수 있어야 한다.
- **FR-6.3** *(연기 — 6.1 종속)* 표시 이름을 변경해도 실제 창 식별 정보는 바뀌지 않는다.
- **FR-6.4** 브라우저 탭은 등록 당시 전체 주소를 보관하며, 이후 다른 페이지로 이동해도 저장된 재실행 주소가 자동으로 바뀌지 않는다.

### FR-7 상태 표시와 갱신
- **FR-7.1** **[1.1 축소]** 상태 구분은 **실행 중 항목 패널**에 한정한다 — 창 그룹 안에서 현재 포커스된 창을 상태 점으로 구분(FR-2.4). ~~저장된 항목(작업 묶음 카드 내 리소스)의 활성/비활성/권한필요 구분~~은 **연기**한다(`#D-30`). 도메인 `evaluate_status`/`ResourceStatus`는 구현·테스트되어 있으나 오케스트레이션에 배선되지 않았다(`known-deviations.md#A4`).
- **FR-7.2** **[1.1 축소]** 상태 점 표시는 실행 창 하위 행에 적용한다(저장 리소스 행은 연기).
- **FR-7.3** **[1.1 연기]** 비활성 항목 흐림 처리 — 저장 리소스 상태 판정(FR-7.1)에 종속되므로 함께 연기.
  > **되돌릴 근거**: 배선 지점은 `vc-app`이 `vc_core::evaluate`를 호출해 `Resource.status`를 채우고 프론트 `Resource` 타입에 `status`를 추가하는 것뿐이다. 도메인 쪽 작업은 이미 끝나 있다.
- **FR-7.4** 실행 중 항목과 저장된 항목의 상태를 주기적으로 자동 갱신한다.
- **FR-7.5** 앱이 보이지 않거나 창 크기 조절 중에는 불필요한 반복 조회를 줄인다. (→ NFR-성능)
- **FR-7.6** 갱신 작업이 오래 걸려도 같은 작업이 겹쳐 실행되지 않는다. (동시성 가드)

(→ AC-22)

(→ AC-13)

- **FR-10.5 (macOS)** 코드 편집기는 등록한 작업 폴더를 새 창으로 다시 열 수 있어야 한다. (→ AC-6)

- **FR-10.7 (macOS)** 일반 앱 창 활성화 시 브라우저 탭 탐색을 수행해 응답이 지연되지 않아야 한다. (→ AC-10)

- **FR-10.12 (Windows)** **[1.1 유지 — 부분 구현, 아래 정합화 노트]** 브라우저 탭 구분. **정정(2026-09-09)**: `WinBrowserTabReader`는 더 이상 통짜 스텁이 아니다 — 라이브 `list_tabs`(제목+활성여부)·`activate_tab`(정확한 탭 전환)·작업 묶음 개별 등록(`BrowserTabLive`)이 UI Automation으로 **구현됨**(아래 정합화 노트, `#B3`/§H). 여전히 **스텁인 것은 capture용 `read_tabs`(제목+URL)뿐**이며, URL이 필요한 영속 캡처 경로(FR-9.1~9.3의 URL 부분, AC-9)만 미충족으로 남는다(`#D-40`, DevTools 프로토콜 필요). 창 단위 분리(FR-2.8)와는 별개 작업임에 유의 — `EnumWindows`로는 탭이 보이지 않는다.
- **FR-10.13 (Windows)** ~~트레이 상주 + 전역 단축키~~ → **[1.1 범위 제외]** 미구현이며(`#D-41`), 현 제품은 일반 창 앱으로 확정한다. 트레이/전역 단축키는 별도 제품 결정이 필요한 항목으로 판단하여 요구사항에서 제외한다.

> **구현 정합화 노트 — Windows 브라우저 탭(FR-9 / FR-10.12), 2026-09-09 착수·구현.** 사용자 요청("지원 브라우저의 현재 열린 탭을 개별 세션으로 확인·선택; 선택 시 정확히 그 탭 활성화")에 따라 Windows에서 Chrome/Edge(및 Brave/Whale) 탭을 **관리형 UI Automation**(`System.Windows.Automation`, .NET Framework 동봉 → `powershell.exe`가 이미 로드 가능)으로 열거·활성화한다. 실행 리소스 **좌측 패널**에서 브라우저 그룹을 펼치면 탭이 개별 행으로 보이고(활성 탭 = 녹색 점, FR-2.4), 클릭 시 해당 창을 최전면화한 뒤 정확히 그 탭을 `SelectionItemPattern.Select`로 선택한다(FR-2.8/4.1/4.2). 탭 컨테이너=`ControlType.Tab`, 탭=`TabItem`만 취하므로 `+`/탭 목록/설정 버튼을 탭으로 오인하지 않는다(FR-9.6). 탭 읽기는 **그룹 펼침 시 온디맨드**로만 수행하고 1초 폴링에는 절대 태우지 않아 창 활성화 지연을 유발하지 않는다(FR-10.7의 취지를 Windows에도 동일 적용).
>
> **문서화된 한계(수용):** ① UIA는 **활성 탭의 제목**만 신뢰성 있게 노출하고 개별 탭의 **주소(URL)는 제공하지 않는다** → FR-9.1(제목+주소 수집)의 **주소 부분은 Windows 좌측 패널 라이브 탭에는 적용 불가**. FR-9.7("주소를 임의로 추측하지 않는다")에 따라 **주소를 지어내지 않고 제목만** 표시한다. 따라서 이 라이브 탭 경로는 **표시·활성화 전용**이며, 탭을 **작업 묶음에 영속 등록**하는 것(FR-9.2/9.3, AC-8/9)은 URL이 필요하므로 여전히 `WinBrowserTabReader::read_tabs`(캡처용, 현재 빈 스텁 — DevTools 프로토콜 필요)의 별개 범위로 남는다. ② Chromium은 창별 접근성 트리를 **지연 생성**하므로 **최전면/관여된 브라우저 창의 탭만** 안정적으로 읽힌다. 완전 백그라운드 창은 탭이 안 보일 수 있고, 그 경우 좌측 패널은 해당 앱의 **OS 창 목록으로 자연 폴백**(요구사항 #1의 창 단위 표시는 그대로 유지)하고 안내 문구를 보인다. 단, **활성화**는 대상 창을 먼저 최전면화하면서 트리를 강제 생성하므로 백그라운드 창의 탭도 전환된다. macOS는 캡처용 탭(제목+URL, `MacBrowserTabReader`)은 있으나 라이브 패널 탭 세션은 아직 미제공(앱 창으로 폴백).
>
> **보완 정합화 노트 — 라이브 탭의 작업 묶음 등록(FR-9 / AC-20 확장), 2026-09-09.** 위 ①에서 "URL이 필요하므로 연기"로 남겼던 **탭의 작업 묶음 영속 등록**을, **URL 없이 제목 기반**으로 구현하여 보완한다(FR-9.7 준수 — URL을 지어내지 않는다). 라이브 탭을 좌측 패널에서 그룹으로 **드래그하면** 새 리소스 종류 **`BrowserTabLive`**로 등록된다: `descriptor`/표시이름 = **탭 제목**, `hint` = `<browser>\u{1f}<hwnd>\u{1f}<idx>`(비영속 활성화 토큰, FR-11.4), `reopen_info` = **없음(URL 미저장)**. 같은 탭(browser+창+인덱스 = 동일 hint)은 한 묶음에 **중복 등록되지 않으며**(FR-3.4), 같은 창의 다른 탭(다른 인덱스)은 각각 등록된다. 등록된 탭을 활성화하면 저장된 토큰으로 정확히 그 탭을 최전면화하고(FR-4.1/4.2), 토큰이 낡았으면(브라우저 재시작·탭 이동) 해당 브라우저를 재열거해 **제목으로 재매칭**한다(찾지 못하면 실패 보고 — 앱만 최전면화는 성공 아님). 복원(FR-9.5)도 **탭 재포커스 전용**이며 URL을 열지 않는다. 이로써 **URL을 얻을 수 있는 캡처 경로**(`read_tabs`, DevTools)만이 잔여 후속으로 남는다. 도메인 대조: 기존 `BrowserTab`(URL 보유, 캡처용)과 **구분되는** 신규 종류이며 6→7개로 확장(PBT-02 라운드트립 대상 포함).

### FR-11 데이터
- **FR-11.1** 모든 데이터는 기본적으로 사용자 컴퓨터에 저장한다.

- **FR-11.3** 리소스는 종류·표시 이름·앱 정보·창 식별 정보·실행 중 연결 정보·재실행 주소/경로를 저장할 수 있어야 한다.

- **FR-11.5** 저장 오류 시 기존 파일과 메모리 상태가 어긋나지 않아야 한다. (→ SECURITY-15)

- **FR-11.8** 코딩 세션 리소스는 **도구 식별자**와 **세션 파일 위치/세션 ID**를 저장한다. 대화 내용 자체는 저장소에 보관하지 않고 표시 시점에 로컬 세션 파일에서 읽는다. (개인정보 최소 저장 — NFR-S1)

### FR-12 코딩 에이전트 세션 (AI Coding Agent Sessions)
- **FR-12.1** "코딩 세션"을 **별도 리소스 유형**으로 등록할 수 있어야 한다. 이번 반복은 **Claude Code**를 우선 지원하며, Codex·OpenCode 등 다른 도구를 추가할 수 있도록 **확장 가능한 구조**(도구별 어댑터)로 설계한다.
- **FR-12.2** 세션 정보는 각 도구가 **로컬에 저장하는 세션/트랜스크립트 파일**을 읽어 수집한다. (예: Claude Code의 프로젝트 세션 로그 — `~/.claude/projects/<프로젝트>/*.jsonl`; 구체 경로·형식은 설계 단계 확정). 외부 서버 전송이나 원격 API 호출 없이 **로컬 파일만** 사용한다. (→ NFR-S1)
- **FR-12.3** **[1.1 축소]** 등록된 세션에 대해 **마지막 질문**과 **답변 완료여부**를 표시한다. ~~세션의 전체 대화 내용(스크롤 열람)~~은 **인앱 열람에서 제외**하고, 전체 대화는 "View"(`activate_coding_session`)로 **실제 터미널을 최전면**에 띄워 그곳에서 읽는 방식으로 대체한다(`#D-38`).
  > **개정 사유**: 인앱 대화 패널은 커밋 이력상 의도적으로 제거되었고, 살아 있는 터미널로 점프하는 편이 "이어서 대화한다"는 실사용 목적에 더 부합한다. `SessionSnapshot.conversation`은 계약에 남아 있어 언제든 되돌릴 수 있다. (→ AC-17 개정)
- **FR-12.4** 답변 완료여부는 최소한 **"사용자 입력 대기 중"**(에이전트가 질문 후 사용자 답변을 기다림)과 **"대기 없음/진행·완료"**를 구분해야 한다. 판별이 불가한 경우 "알 수 없음"으로 표시하고 임의로 단정하지 않는다.
- **FR-12.5** 세션의 대화 내용과 상태는 **주기적으로 자동 갱신**하여 세션 파일 변경을 반영하며, FR-7.4~FR-7.6의 갱신 정책(폴링 상한·불필요 조회 억제·중복 실행 방지)을 따른다.
- **FR-12.6** 대화 내용은 **읽기 전용**으로 표시하며, 앱은 세션 파일을 수정·삭제하지 않는다. (→ AC-19)
- **FR-12.7** 세션 리소스도 활성·비활성·권한 필요 상태(FR-7.1)를 가진다. 세션 파일이 없거나 접근 불가하면 비활성/권한 필요로 표시하고, 확보하지 못한 대화 내용을 임의로 추측하지 않는다. (cf. FR-9.7)
- **FR-12.8** 세션 리소스 활성화 시, 식별 가능한 경우 해당 세션이 실행 중인 **연결된 터미널/에디터 창을 최전면**으로 가져온다. (best-effort — 도구·OS별 가능 범위 내; 불가 시 세션 상세 보기로 대체)
- **FR-12.9** 대화 내용에 민감 정보가 포함될 수 있으므로, 대화 내용은 **로그로 출력하지 않는다**. (→ SECURITY-03)

### FR-13 앱 기동 (Boot) — **[1.1 신설]**
> 구현 완료된 기능의 **사후 정식 승격**(커밋 `7ab755a`). 원 요구사항에 없었으며 `drift-analysis.md#D-01`로 검출되었다.

- **FR-13.1** 앱 기동 시 **전체 화면 스플래시**를 표시하고, 최초 로드가 끝날 때까지 그 아래의 모든 UI 입력을 **차단**한다. 창이 "조작 가능해 보이지만 비어 있는" 상태를 노출하지 않는다.
- **FR-13.2** "최초 로드 완료"의 기준은 **① 저장된 작업 묶음 로드 · ② Claude 연결 상태 조회 · ③ 첫 실행앱 스캔**의 완료(성공·실패 무관)로 한다. 실행앱 스캔은 OS 호출이라 가장 느리며, 스플래시가 존재하는 주된 이유다.
- **FR-13.3** 스플래시는 **최소 표시 시간**을 두어 빠른 기동에서 깜빡임으로 보이지 않게 한다(현행 650ms).
- **FR-13.4** 어떤 백엔드 호출이 지연·중단되어도 **하드 캡**(현행 8초) 이후에는 반드시 스플래시가 걷히며, UI가 영구히 갇히지 않는다. (→ NFR-R1, SECURITY-15 페일세이프)
- **FR-13.5** 스플래시는 페이드아웃 후 **언마운트**되어 이후 렌더·입력에 영향을 주지 않는다.
- **FR-13.6** 스플래시는 앱 UI와 동일한 시각 언어(EP-133 모티프)를 따르고, 보조기술을 위해 진행 상태 역할(`role="progressbar"`, `aria-busy`)을 노출한다.
- **FR-13.7** 스플래시 이전(프리마운트) 구간에도 흰 화면이 노출되지 않도록 문서 배경색을 즉시 칠한다.
- **FR-13.8** 인트로 시각 구성 — **[1.3 신설]** 도구 "패드" 블럭은 **랜덤 산포가 아니라 화면 중앙에 가로로 정렬된 5줄 그리드**로 배치하며, 그리드는 **뷰포트 가로 폭을 가득 채운다**(열 개수를 뷰포트 너비에 맞춰 계산, 좌우 여백 최소). 중앙에는 **로고**(오렌지 레코드-닷 마크 + `vibe control` 워드마크)를 두어 **명확한 초점**으로 삼는다. 패드의 기존 디자인(패드 면·글리프·탭 활성 플래시)은 **유지**하되, 사용자의 시선이 분산되지 않도록 최종적으로 **낮은 불투명도(현행 0.24)로 흐릿하게** 유지하여 **로고보다 강조되지 않게** 한다. 단 초기 활성화 구간에는 패드를 **더 선명하게(≈0.62) 보이다가 로고가 등장할 때 흐릿하게 낮춘다** — 초점이 패드에서 로고로 자연스럽게 넘어가도록. 패드 활성 플래시는 브랜드 오렌지를 기준으로 한 **조화로운 다중 색상 팔레트**(`--hue`)로 다양하게 빛나되 로고를 넘어서지 않는다. 활성화는 중앙에서 바깥으로 퍼지는 리플 순서를 따르며(패드 수와 무관하게 일정한 스윕 시간), 이후 로고가 초점으로 자리잡는다. (구현: `frontend/src/App.tsx` `Splash`, `styles.css` `.intro-*`)

## 4. 비기능 요구사항 (Non-Functional Requirements)

### NFR-플랫폼
- **NFR-P1** 지원 환경: macOS 12 이상, Windows 10/11.
- **NFR-P2** OS별 기능은 각 OS 실제 환경에서 별도로 빌드·검증한다.
- **NFR-P3** macOS·Windows용 설치 가능한 빌드 산출물을 생성한다. (→ 완료 기준)

### NFR-성능/반응성
- **NFR-Pf1** 상태 갱신이 입력·창 조작을 방해하지 않아야 한다. (→ AC-10)
- **NFR-Pf2** 접근성 탐색·창 열거는 처리 개수와 탐색 깊이에 상한을 둔다.
- **NFR-Pf3** 앱이 보이지 않거나 리사이즈 중에는 폴링을 줄이고, 갱신 작업의 중복 실행을 방지한다. (동시성 가드)
- **NFR-Pf4** 앱 아이콘은 캐시하여 반복 추출 비용을 줄인다.

### NFR-신뢰성/오류 처리
- **NFR-R1** 주요 실패 상황에서 앱이 종료되지 않고 원인을 사용자에게 알린다. (→ SECURITY-15, FR-5.3)
- **NFR-R2** 전체 활성화 중 일부 실패가 나머지 처리를 막지 않는다. (→ AC-11)

### NFR-프라이버시/보안 (Security Baseline 적용 — 상세 §6)
- **NFR-S1** (개정 2026-09-08) 앱은 사용자의 문서 내용·작업 묶음·코딩 세션 **데이터**를 자동으로 외부 서버로 전송하지 않는다. 코딩 세션 열람(FR-12)은 로컬 파일만 읽으며 네트워크 호출이 없다. **예외**: 사용자가 명시적으로 입력하는 앱 내 Claude 콘솔 프롬프트는 NFR-S3의 규정에 따라 외부 전송된다(작업 묶음/세션 데이터의 자동 전송은 여전히 금지).
- **NFR-S2** 파일 경로·웹 주소는 문자열 명령 조합이 아니라 OS 실행 기능의 **인자로 전달**한다. (→ SECURITY-05 injection prevention)
- **NFR-S3** (신설 2026-09-08 — 앱 내 Claude 프롬프트 콘솔) 콘솔은 **사용자가 명시적으로 입력한 프롬프트만** AWS Bedrock 런타임으로 **HTTPS 전송**한다. 인증 토큰(Bedrock API 키)은 하드코딩·로그·UI 노출 금지이며 로컬 설정(OS config 디렉터리, 리포 밖)에만 저장한다. 작업 묶음·세션 대화·문서 내용을 자동 첨부하지 않는다. 상세: `construction/vc-app/claude-console/design.md`. (→ SECURITY-01 transit, SECURITY-12 자격증명)

### NFR-사용성/문서
- **NFR-U1** 데이터 저장 위치·권한 설정 방법·기본 사용법을 사용자 문서로 제공한다. (→ 완료 기준)

## 8. 인수 조건 (Acceptance Criteria)

macOS·Windows 실제 환경에서 확인한다.

- **AC-1** 작업 묶음 생성·항목 추가 후 재실행해도 내용 유지 (FR-1.4)
- **AC-2** 실행 중 항목 더블 클릭 시 정확한 창/탭 최전면 (FR-2.6, FR-4.1)
- **AC-3** 실행 중 항목을 드래그하면 한 번만 등록 (FR-3.1, FR-3.4)
- **AC-4** 같은 앱의 서로 다른 창을 같은 묶음에 등록 (FR-3.5)
- **AC-5** 경로가 다른 두 폴더 창을 구분·각자 원래 경로로 재오픈 (FR-3.5, FR-10.4)
- **AC-6** 서로 다른 작업 폴더의 코드 편집기 창 구분·각자 복원 (FR-10.5, FR-10.11)
- **AC-7** 실제 브라우저 탭 수와 목록의 탭 수 일치 (FR-2.7, FR-9.6). **정정(2026-09-09)**: Windows도 라이브 `list_tabs`(UIA)로 탭을 수집한다(더 이상 통짜 스텁 아님, FR-10.12). 단 Chromium 지연 접근성 트리로 **최전면/관여 창의 탭만** 안정 수집(백그라운드 창은 창 목록 폴백). macOS는 캡처 경로로 전량 일치.
- **AC-8** *(macOS 한정 — Windows 미충족)* 같은 주소 탭 2개 중 하나를 닫아도 다른 탭으로 오연결 안 됨 (FR-9.2).
- **AC-9** 저장 탭을 닫은 뒤 재실행하면 등록한 전체 주소가 열림 (FR-4.3, FR-9.3)
- **AC-10** 메신저 대화 창 활성화 시 장시간 응답 대기 없음 (FR-10.7, NFR-Pf1)
- **AC-11** 전체 활성화 중 일부 실패해도 나머지 처리 (FR-5.3, NFR-R2)
- **AC-12** 묶음 삭제 후 재실행해도 삭제 항목 재등장 안 함 (FR-1.1, FR-1.4)
- **AC-13** *(미충족 — 백로그)* 권한 필요한 OS에서 실제 권한 상태와 안내 일치 (FR-10.2). `PermissionChecker` 부재로 현재 검증 불가.
- **AC-14** **[1.1 개정]** 패널/카드 크기를 **조절할 수 있다**(FR-8.3, FR-8.5). ~~재실행 후 유지~~는 FR-8.10 연기에 따라 **현 반복 인수 대상에서 제외**한다.
- **AC-15** 고해상도 화면에서 앱·브라우저 아이콘 선명 (FR-8.7)
- **AC-16** 등록한 Claude Code 세션 카드에서 **마지막 질문**과 **답변 완료여부**(대기 중/대기 없음)가 실제 세션 상태와 일치 (FR-12.3, FR-12.4)
- **AC-17** **[1.1 개정]** 세션 카드의 **마지막 질문·완료여부 표시가 세션 진행에 따라 자동 갱신**되고, "View"로 해당 세션의 **터미널이 최전면**에 온다 (FR-12.3 개정판, FR-12.5, FR-12.8).
- **AC-18** 세션 파일이 손상되거나 일부만 있어도 앱이 종료되지 않고 가능한 범위를 표시 (FR-12.7, SECURITY-13/15)
- **AC-19** 앱은 세션 파일을 수정하지 않는다(읽기 전용) (FR-12.6)
- **AC-21** **[1.1 신설 · 1.3 보강]** 앱을 실행하면 스플래시가 즉시 나타나 그 아래 UI로 **클릭이 전달되지 않으며**, 묶음·Claude 상태·첫 실행앱 목록이 모두 채워진 뒤에 걷힌다. 백엔드 호출이 지연되어도 8초 안에는 반드시 걷혀 앱이 조작 가능해진다 (FR-13.1~13.5). **[1.3]** 인트로의 패드는 화면 중앙에 **가로 5줄 그리드**로 정렬되고(랜덤 산포 아님), 중앙 **로고**가 초점으로 나타나며, 패드는 **흐릿하게(저불투명도)** 유지되어 로고보다 강조되지 않는다 (FR-13.8)
- **AC-20** 창이 여러 개인 앱을 클릭하면 창/탭 목록이 펼쳐지고, 특정 창/탭을 선택하면 정확히 그 창만 최전면으로 온다(다른 창을 대신 보여주지 않음); 창이 하나인 앱도 동일 상호작용으로 그 창을 활성화하며, 닫힌 창은 갱신 후 목록에서 사라진다 (FR-2.8, FR-2.2/2.4/2.6, FR-4.1/4.2)
- **AC-22** **[1.3 신설 2026-09-09]** 윈도우 버전을 실행하면 OS 기본 **제목표시줄이 표시되지 않고**, 맥 버전과 **동일한 화면**(좌측 실행앱 패널 + 우측 카드, 상단 여백 포함)이 나온다. 상단 영역 드래그로 창 이동이 되고 창 크기 조절이 가능하다. **좌상단에 맥 신호등을 모사한 닫기/최소화/최대화 버튼이 있고, 각 버튼에 구분용 심볼(× / − / □)이 표시되며 각각 실제로 창을 닫기/최소화/최대화한다** (FR-8.11, FR-8.6)

## 10. 핵심 요구사항 요약

- **크로스플랫폼(Tauri) 데스크톱 앱**으로 macOS·Windows에서 앱/창/브라우저 탭/폴더/**코딩 에이전트 세션**을 "작업 묶음"으로 저장·복원한다.
- **코딩 세션 리소스**(우선 Claude Code)는 로컬 세션 파일을 읽어 전체 대화·마지막 질문·답변 완료여부를 읽기 전용으로 표시하며, 확장 가능한 도구별 어댑터 구조를 둔다.
- **정확한 창·탭 식별과 재실행**(닫힌 항목은 저장 주소/경로로 복원)이 핵심 가치이며, OS별 접근성/UI Automation과 브라우저 주소 수집이 기술적 난제다.
- **견고한 로컬 저장**(단일 JSON, 원자적 교체, 버전 마이그레이션)과 **부분 실패 허용 전체 활성화**가 신뢰성 축이다.
- **Security(Full)**·**PBT(Partial)** 확장을 적용하며, 특히 입력 검증·명령 인자 분리·예외 처리·직렬화 round-trip을 강제한다.
